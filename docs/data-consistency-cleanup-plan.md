# 数据一致性清理：本地降级数据回填与垃圾清除

- 分支：`feature/data-consistency-cleanup`
- 关联文档：`docs/design.md`（数据层分层与降级约定）、`checklist.md`
- 状态：已实现，待验收

## 1. 背景

各数据域采用「优先 PostgreSQL / R2，失败时回退本地文件」的存储策略，回退实现集中在：

| 本地文件 | 定义位置 | 覆盖数据域 |
| --- | --- | --- |
| `.data/watchlist.json` | `src/lib/watchlist.ts` | 自选股 |
| `.data/fund-watchlist.json` | `src/lib/fund-watchlist.ts` | 自选基金 |
| `.data/stock-portfolio.json` | `src/lib/stock-portfolio.ts` | 个股持仓 |
| `.data/fund-positions.json` | `src/lib/fund-position.ts` | 持有基金 |
| `.data/alerts.json` | `src/lib/alert-store.ts` | 预警规则与事件 |
| `.data/alert-settings.json` | `src/lib/alert-store.ts` | 预警设置（**非降级**，DB 模式下也读写） |
| `.data/daily-reports/{kind}/*.json` | `src/lib/daily-report-store.ts` | 日报（R2 云端优先，本地为兜底/索引） |

两个已知问题：

1. **粘性降级且不回填**：降级开关是「进程内一次性切换」，一旦失败，本次运行内不会再回到数据库；DB 恢复后文件里的数据不会自动并入数据库。
2. **失败静默**：数据库不可用（例如迁移未应用导致 `fund_positions` 表缺失）时，界面照常写入本地文件，用户无法察觉「这些数据其实没进库」。

实测案例：DB 迁移停在 `0009`，`drizzle/0010` 才建 `fund_positions`，导致持有基金长期写入本地文件；用户录入的持仓、定投计划、跨日结算结果全部只存在于本地。

## 2. 目标

在数据库（日报场景为 R2）确认可用的前提下，提供一次「数据一致性清理」：

- **确定性事实数据**（用户录入的股票/基金条目、持仓、预警规则、AI 生成的日报）→ 回填到数据库/云端。
- **模板化垃圾数据**（数据源或数据库断连时由系统生成的占位内容）→ 从 `.data` 清除（隔离）。
- 同一能力同时提供 **CLI 脚本** 与 **工作台右上角手动入口**。

## 3. 数据分类规则

### 3.1 文件级分类

| 分类 | 判定 | 处置 |
| --- | --- | --- |
| `keep` | `alert-settings.json`（非降级文件） | 不动，仅在报告中说明 |
| `restore` | 文件内存在需回填条目 | 回填 DB/R2 后隔离文件 |
| `clean` | 文件为空结构（`[]`、`{"rules":[],"events":[]}`）或全部内容为模板垃圾 | 直接隔离 |
| `archive` | 内容与数据库完全一致（纯陈旧镜像） | 归档隔离，保留数据库为准 |
| `report-only` | 未在白名单内的文件 | 只报告，不处理 |

### 3.2 条目级判定（自选股 / 自选基金 / 个股持仓 / 持有基金 / 预警条目）

判定基准是**数据更新时间**，而不是单纯的内容差异。参与比对的两个时间是：本地降级文件的磁盘修改时间（`mtime`）、数据库该数据域的**最后改动时间**（对应表 `added_at` / `updated_at` / `created_at` 的最大值）。

| 判定 | 条件 | 动作 |
| --- | --- | --- |
| `insert` | 数据库无该主键 | 写入数据库 |
| `redundant` | 数据库有该主键，且内容指纹一致 | 丢弃：两侧本就是同一条数据 |
| `redundant` | 数据库有该主键、内容不同，但数据库最后改动时间**不早于**本地文件修改时间 | 丢弃：本地是老旧冗余数据 |
| `update` | 数据库有该主键、内容不同，且数据库最后改动时间**早于**本地文件修改时间 | 数据库版本落后 → 以本地为准覆盖 |
| `invalid` | 主键缺失/非法（非 6 位代码等）、金额或收益非有限数值 | 丢弃：模板垃圾 |

补充约束：

- 内容指纹由两侧共用的实现生成（`src/lib/data-consistency-signature.ts`）：数值统一到 4 位小数（数据库 `numeric` 列以字符串返回，需要与本地 `number` 对齐）、字符串去首尾空白、空串与「字段全为空」的子对象等同于 `null`，避免把表示上的差异误判成内容差异。
- 任一侧时间不可解析（读不到数据库时间戳或文件 `mtime`）时保守处理：不覆盖数据库，只按冗余处理，并在报告里写明原因。
- 判定为 `update` 的条目必须在同一次执行里真正写入；若某数据域没有覆盖写入能力，则**保留本地文件**并记入错误列表，不能只把文件挪进隔离目录。

### 3.3 占位名处理

数据源不可用时，自选条目名会被本地兜底为 `股票 600519` / `基金 560710` 这类占位名（`src/lib/code-verify.ts#isPlaceholderName`）。

占位名本身是系统生成的模板文本，但**它承载的代码与备注是用户输入的事实数据**，因此规则是：

- 记录照常回填，**不因为占位名而丢弃整条数据**；
- 报告中把该条标注为「占位名，待名称自愈」，名称回填仍交给既有的 `repairWatchlistNames` 流程，避免在清理动作里耦合数据源可用性。

### 3.4 日报

| 情况 | 判定 |
| --- | --- |
| R2 未配置 | 本地即唯一存储 → 全部保留，不清理 |
| R2 已存在同一篇（`kind` + `date`） | 本地副本冗余 → 清除本地副本 |
| R2 缺失且本地 `source === "deepseek"` | 用户在断连期间生成的正式日报 → 回填 R2 |
| R2 缺失且本地 `source === "template"` | 数据源断连时的模板降级稿（正文含「本日该数据不可用」等占位文案）→ 清除 |

## 4. 安全策略

1. **就绪门槛**：只有数据库健康状态为 `ready` 才允许执行；否则接口只返回扫描结果并拒绝写库。健康检查包含连接探测、关键表存在性（`to_regclass`）与迁移进度（`drizzle.__drizzle_migrations` 与 `drizzle/meta/_journal.json` 条数比对），可提前发现「迁移落后导致降级」这类故障。
2. **先扫描后执行**：`GET` 只读扫描，`POST` 才落地；前端默认展示扫描计划，需再点一次「执行清理」。
3. **清除可回滚**：所有清除都是移动到 `.data/quarantine/<yyyyMMddHHmmss>/` 下的同名路径，不做物理删除。
4. **白名单**：只处理上表列出的固定路径，未知文件只报告。
5. **不触碰非降级文件**：`alert-settings.json` 与运行中的日志不在处理范围。

## 6. 验收方式

- 单测：分类规则、条目级判定（内容一致 / 数据库更旧 / 数据库更新 / 时间不可读四种分支）、内容指纹归一化、日报分类、路径安全、DB 未就绪拒绝执行。
- 静态：`corepack pnpm typecheck`、`lint`、`test`、`build`。
- 端到端：dev 3000 真机造一份「DB 缺失 + 本地有数据」的场景，验证扫描 → 执行 → 数据库出现数据 → 文件被隔离。

## 7. 风险与遗留

- 条目级判定的依据是「数据库最后改动时间 vs 本地文件修改时间」：若用户在断连期间改了本地文件、而数据库之后又被写入过内容，本地版本会被判为冗余（文件仍归档在 `.data/quarantine/`，可人工取回）。报告会逐条给出两个时间戳，覆盖前请先人工核对。
- `update` 判定会覆盖数据库同一主键的记录，因此执行前必须先在扫描结果里确认。
- 降级仓储的粘性开关未改动（本次不扩大范围）：执行清理后若进程仍处于降级态，需要重启服务才会切回数据库读写。
- 日报的模板/正式判定只依赖 `source` 字段；历史上若存在 `source` 缺失的旧日报，会按「非 deepseek」处理，存在被清理的可能，报告会明确列出。
